# 任务调度模块优化清单

> 生成时间：2026-06-18
> 审查范围：任务管理、任务执行、任务依赖、本地调度器、自研调度器（SchedulerX）前后端代码
> 状态：待确认执行

---

## 1. 前端：N+1 查询导致 DAG 依赖图加载极慢

**涉及文件：** `mdatax-web/src/components/DependencyGraph.vue`

**问题描述：** `enrichDependency` 对每个依赖项都单独发一次 HTTP 请求获取上游/下游任务详情。如果某个任务有 20 个上游依赖，就会触发 20 次串行 HTTP 调用，页面加载时间随依赖数量线性增长。

**影响：** 依赖关系稍复杂时页面白屏数秒，用户体验极差。

**建议优化方案：** 后端提供批量查询接口（如 `/task/batch?ids=1,2,3`），前端一次性拉取所有关联任务信息；或后端 `/task/{id}/dependencies` 直接返回填充好的任务名称/编码。

## 2. 前端：缺少请求错误处理，静默失败

**涉及文件：** `mdatax-web/src/components/TaskFormDialog.vue`、`DependencyGraph.vue` 等

**问题描述：** 多处 API 调用使用空的 `catch` 块静默吞掉错误：
- `TaskFormDialog.vue`：`loadUsers` 失败无提示
- `TaskFormDialog.vue`：`loadDatasources` 失败无提示
- `DependencyGraph.vue`：依赖详情加载失败仅 `push(dep)`

**影响：** 用户无法感知数据加载失败，表单中下拉框为空时无反馈。

**建议优化方案：** 至少记录 `console.error` 并给出 `ElMessage.warning` 提示。

---

## 3. 前端：状态值硬编码（魔法值）

**涉及文件：** `mdatax-web/src/views/TaskManagement.vue`、`TaskExecutionBoard.vue`、`TaskFormDialog.vue` 等

**问题描述：** 状态值大量硬编码：
- `row.status === 1 ? '启用' : row.status === 2 ? '草稿' : '停用'`
- `status: 2`（草稿）
- 执行状态 `PENDING`、`RUNNING`、`SUCCESS` 等字符串在前端多处重复

**影响：** 状态枚举变更时需要全局搜索替换，极易遗漏。

**建议优化方案：** 前端统一维护 `TASK_STATUS`、`EXECUTION_STATUS` 常量对象，或从后端获取枚举定义。

---

## 4. 前端：手动执行时 `triggerUserId` 固定传 null

**涉及文件：** `mdatax-web/src/views/TaskManagement.vue`

**问题描述：** 手动执行任务时 `triggerUserId: null`，当前登录用户 ID 未传入，导致执行记录无法追溯操作人。

**影响：** 审计日志缺失，无法定位谁手动触发了任务。

**建议优化方案：** 从 Pinia store 或 localStorage 获取当前登录用户 ID 传入。

---

## 5. 后端：分页查询后内存过滤导致分页数据错乱

**涉及文件：** `mdatax-server/src/main/java/com/mogu/data/integration/service/TaskService.java`

**问题描述：** `lastExecutionStatus` 过滤是在分页查询完成后对 `result.getRecords()` 进行内存过滤，然后重新设置 `total`。这会导致：
1. 第 1 页可能只返回 3 条（过滤掉了 7 条），而分页组件显示每页 10 条
2. `total` 被篡改为过滤后的数量，但总页数计算仍基于原始 page/size

**影响：** 分页数据不一致，前端翻页时出现空白页或数据重复。

**建议优化方案：** 将 `lastExecutionStatus` 过滤条件下沉到 SQL 中（JOIN 子查询），或改用先查执行记录再反查任务的两阶段查询。

---

## 6. 后端：循环单查构成 N+1 查询

**涉及文件：** `mdatax-server/src/main/java/com/mogu/data/integration/service/TaskService.java`

**问题描述：** `fillLastExecutionInfo` 对每个任务单独查询最近执行记录，列表页每页 50 条任务就会触发 50 次 SQL 查询。

**影响：** 任务列表接口性能随分页大小线性恶化。

**建议优化方案：** 使用单条 SQL 的 `ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY start_time DESC)` 或先批量查询执行记录再内存映射。

---

## 7. 后端：统计接口多次全表扫描

**涉及文件：** `mdatax-server/src/main/java/com/mogu/data/integration/service/TaskExecutionService.java`

**问题描述：** `getStatistics` 方法中，先 `count(wrapper)` 查总数，然后对每种状态各执行一次 `count(statusWrapper)`，共 7 次全表/范围扫描。

**影响：** 执行记录表数据量大时统计接口响应慢。

**建议优化方案：** 使用单条 SQL `GROUP BY status` 聚合查询，一次扫描完成所有统计。

---

## 8. 后端：平均耗时计算逻辑错误

**涉及文件：** `mdatax-server/src/main/java/com/mogu/data/integration/controller/TaskController.java`

**问题描述：** 计算平均耗时：
```java
TaskExecution avgResult = taskExecutionService.lambdaQuery()
    .eq(TaskExecution::getTaskId, id)
    .eq(TaskExecution::getStatus, "SUCCESS")
    .one();
if (avgResult != null && avgResult.getDurationMs() != null) {
    vo.setAvgDurationMs(avgResult.getDurationMs());
}
```
这里只取了第一条成功记录，根本不是"平均"耗时。

**影响：** 统计指标严重失真，误导用户判断任务性能。

**建议优化方案：** 使用 `SELECT AVG(duration_ms) FROM task_execution WHERE task_id = ? AND status = 'SUCCESS'`。

---

## 9. 后端：事务边界不当，依赖触发在事务内

**涉及文件：** `mdatax-server/src/main/java/com/mogu/data/integration/service/TaskExecutionService.java`

**问题描述：** `finishExecution` 方法上标注 `@Transactional`，但在事务内部调用 `taskDependencyService.triggerDownstreamTasks()`，该方法可能涉及延迟调度、条件表达式求值、下游任务执行。如果下游触发失败或超时，会导致整个事务回滚，当前任务的"成功"状态也会被回滚。

**影响：** 任务状态与执行实际结果不一致，可能出现"执行成功了但记录显示失败"的诡异情况。

**建议优化方案：** 将依赖触发逻辑移到事务外，使用 Spring 的 `TransactionSynchronizationManager.registerAfterCompletion()` 或 `@TransactionalEventListener` 实现事务提交后的异步触发。

---

## 10. 后端：条件表达式求值存在注入风险

**涉及文件：** `mdatax-server/src/main/java/com/mogu/data/integration/service/TaskDependencyService.java`

**问题描述：** `evaluateCondition` 方法使用字符串替换后直接 `split` 和 `parseLong`。如果 `affectedRows` 为 `null` 则替换为 `"0"`，但如果值为负数或包含非数字字符，`Long.parseLong` 会抛异常。如果表达式被构造为 `UPSTREAM_AFFECTED_ROWS > 0 && 恶意代码`，当前实现无法处理。

**影响：** 条件表达式功能受限，且存在潜在的表达式注入风险。

**建议优化方案：** 引入轻量级表达式引擎（如 Spring Expression Language `SpEL` 或 AviatorScript），对变量进行严格类型绑定，避免字符串拼接求值。

---

## 11. 后端：延迟触发调度器配置错误

**涉及文件：** `mdatax-server/src/main/java/com/mogu/data/integration/service/TaskDependencyService.java`

**问题描述：** `scheduleDelayedTrigger` 使用 `CronTrigger("0 * * * * *")` 实现"延迟 N 秒"，这表示"每分钟的第 0 秒执行"，而不是延迟执行。`delaySeconds` 参数被完全忽略。

**影响：** 依赖延迟配置不生效，下游任务在每分钟整点被触发而非按配置的延迟时间触发。

**建议优化方案：** 使用 `taskScheduler.schedule(() -> ..., Instant.now().plusSeconds(dep.getDelaySeconds()))` 或 `new java.util.Date(System.currentTimeMillis() + delaySeconds * 1000)`。

---

## 12. 后端：调度器实现大量抛出 UnsupportedOperationException

**涉及文件：** `mdatax-server/src/main/java/com/mogu/data/integration/scheduler/SqlTaskSchedulerManager.java`、`SyncTaskSchedulerManager.java`

**问题描述：** 两个本地调度器实现对接口的大量方法直接 `throw new UnsupportedOperationException("本地调度器不支持...")`，包括 `triggerTask`、`triggerSqlTask`、`triggerSyncTask` 等。这导致 `TaskService.executeTask()` 调用 `schedulerManager.triggerTask(task)` 时，在 `scheduler.type=local` 配置下会抛出异常，用户无法手动执行任务。

**影响：** 本地调度模式下手动执行任务功能完全不可用。

**建议优化方案：** 本地调度器应实现手动触发能力（直接调用 `sqlTaskEngineService.execute(taskId)` 或 `syncEngineService.execute(taskId, null)`），而非抛出异常。

---

## 13. 后端：循环依赖检测使用递归，存在栈溢出风险

**涉及文件：** `mdatax-server/src/main/java/com/mogu/data/integration/service/TaskDependencyService.java`

**问题描述：** `hasCycle` / `pathExists` 使用深度优先递归检测循环依赖。如果依赖链很深（如 1000 层），可能导致 `StackOverflowError`。虽然 `visited` 集合防止了重复访问，但递归深度仍等于依赖链长度。

**影响：** 极端情况下 JVM 栈溢出，服务崩溃。

**建议优化方案：** 将递归改为基于栈/队列的迭代实现（Kahn 算法已在 `TopologyResolver` 中实现，可直接复用）。

---

## 14. 后端：调度器启动加载未限制任务数量

**涉及文件：** `mdatax-server/src/main/java/com/mogu/data/integration/scheduler/SqlTaskSchedulerManager.java`、`SyncTaskSchedulerManager.java`

**问题描述：** `initOnStartup()` 加载所有启用状态的任务：
```java
List<SqlTask> tasks = sqlTaskService.lambdaQuery()
    .eq(SqlTask::getDeleted, 0)
    .eq(SqlTask::getStatus, 1)
    .list();
```
如果数据库中有数万条启用任务，全部加载到内存并注册调度，会导致启动时间极长、内存占用过高、`ThreadPoolTaskScheduler` 线程池被耗尽。

**影响：** 系统启动失败或调度器无法正常工作。

**建议优化方案：** 分页加载任务，或限制单次加载数量；评估是否需要全量加载，考虑按需加载/懒加载策略。

---

## 15. 自研调度器：超时检测硬编码且未使用任务级配置

**涉及文件：** `mdatax-schedulerx/src/main/java/com/mogu/data/schedulerx/engine/TimeoutChecker.java`

**问题描述：** `timeoutSeconds` 始终为 600 秒，注释也明确说明未实现从配置读取。所有任务统一 10 分钟超时，无法适配长短不同的任务。

**影响：** 长任务被误判超时，短任务失败时延迟 10 分钟才发现。

**建议优化方案：** `TaskInstance` 表增加 `timeoutSeconds` 字段，或在 `DagTask` 配置中存储超时时间，启动时注入到 `TaskInstance`。

---

## 16. 自研调度器：HTTP 回调执行器未设置超时

**涉及文件：** `mdatax-schedulerx/src/main/java/com/mogu/data/schedulerx/executor/HttpCallbackExecutor.java`

**问题描述：** 使用 `httpClient.newCall(request).enqueue(...)` 异步发送请求，但未设置连接超时、读取超时、写入超时。如果下游服务无响应，回调请求会挂起直到操作系统级别的 TCP 超时（通常数分钟）。

**影响：** 任务状态长时间不准确，超时检测器也无法正确判定超时。

**建议优化方案：** 在 `OkHttpConfig` 中为 `OkHttpClient` 配置明确的 `connectTimeout`、`readTimeout`、`writeTimeout`（如 30 秒）。

---

## 17. 自研调度器：状态机缺少 KILLED 状态转换

**涉及文件：** `mdatax-schedulerx/src/main/java/com/mogu/data/schedulerx/engine/StateMachine.java`

**问题描述：** `RUNNING` 状态只能转换为 `SUCCESS`、`FAILURE`、`TIMEOUT`，缺少 `KILLED`（人工终止）的转换路径。`DagEngine.kill()` 方法直接将任务状态设为 `FAILURE`，而非专门的终止状态。

**影响：** 无法区分"自然失败"和"人工终止"，影响运维排查和统计准确性。

**建议优化方案：** 增加 `EventType.KILL` 和 `TaskInstanceStatus.KILLED`，状态机中允许 `RUNNING -> KILLED` 转换。

---

## 18. 自研调度器：DAG 引擎并发安全问题

**涉及文件：** `mdatax-schedulerx/src/main/java/com/mogu/data/schedulerx/engine/DagEngine.java`

**问题描述：** 多处存在竞态条件：
1. `start()` 方法：查询 `dagInstance` 后检查状态，再更新为 `RUNNING`，两个操作之间没有分布式锁，并发调用可能导致重复启动。
2. `onTaskComplete()`：任务完成回调可能被多次调用（如网络重试），状态机转换前未校验当前状态是否已变化。
3. `kill()`：查询 `RUNNING` 任务列表后逐个更新，期间可能有新任务进入 `RUNNING` 状态，导致漏杀。

**影响：** 同一 DAG 实例被重复启动、任务状态被覆盖、终止操作不彻底。

**建议优化方案：**
- 使用数据库乐观锁（`version` 字段）或分布式锁（Redis/DB）保护 DAG 实例状态变更
- 任务状态更新使用 `UPDATE ... WHERE status = 'RUNNING'` 的原子操作
- `kill()` 操作后再次扫描确认无遗漏的 `RUNNING` 任务
